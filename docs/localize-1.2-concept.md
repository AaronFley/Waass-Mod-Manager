# 一键汉化（1.2.0 方案草案）

写于 2026-10-28。所有数字都来自本机真实游戏目录的只读实测，不是估的。

---

## 一、先看清现状：36 条该翻，卡在 5 个手工步骤上

用现在这版程序的体检接口扫了一遍真实库：

| 项目 | 数量 |
|---|---|
| 带语言表的模组 | 15 |
| 中文语言表里**已经是中文**的条目 | **792** |
| 语言表里**仍是英文**的条目 | **45** |
| ├ 菜单项（菜单页里能点到、能看懂的开关） | **31** |
| ├ 菜单分组名（`Other`、`Mod by … / Auto Equip` 这类标题） | **5** |
| ├ 模组显示名（`Hoods`、`Light Rewrite`、`User Interface: Remastered Edition`） | 5 |
| └ 游戏内物品名（`Deadly Ronin's Kimono` 等 4 件护甲） | 4 |
| **默认该翻的合计** | **36** |
| 语言表加密、读不出原文 | 3 个（Blood And Steel / PTOptimization / StandardisedNaming） |

**「不改模组名、只翻菜单页」这条口径一确立，数字就从 45 掉到 36，而且难度结构完全变了。**
剩下 9 条不是「翻不了」，是「翻了容易出事」，所以默认不勾、但保留手动勾选：

- **模组显示名**（5 条）：`Hoods`、`Light Rewrite`、`User Interface: Remastered Edition`。
  这些名字会被 Script Merger 台账、Nexus 追踪、我们自己的 `names.json`、
  以及**用户发的求助截图**同时引用。改一个地方就对不上，排查成本极高。
  收益只是「菜单里看着是中文」，不划算。
- **游戏内物品名**（4 条）：`Deadly Ronin's Kimono` / `Pants` / `Footwear` / `Glove`
  是 dlc 的护甲件名，显示在物品栏和装备栏。它们不是「菜单页」，
  而且汉化后会和游戏本体物品命名风格不一致（本体是「华丽的浪人甲」这类）。
  想看中文可以手动勾，但默认不动。

**还有一个更关键的发现：默认口径下，36 条全部集中在 `hoods Switchable Cloak` 一个模组里。**
其他 14 个模组的待翻条目全是模组名或物品名。也就是说 —— 本机现在点一次「一键汉化」，
真正会动的只有一个模组。

这不是坏消息，恰恰说明**一键的价值在将来**：新装一个 mod、它带了 200 条英文菜单，
今天要来回倒 5 遍 JSON，明天点一次就完事。所以这一版把引擎和流程做对，
比现在能翻多少条重要得多。

**「实用性低」的真正来源**也不是量，是为这 36 条要走的工序：

1. 点「提取」——**一次只能提一个模组**，45 条散在 5 个模组里，至少要来回 5 轮；
2. 程序生成一个 JSON 文件，记下路径；
3. 打开 AI 对话，把这个 JSON 的内容贴进去，再解释一遍「请填 dst 字段、注意别超长」；
4. 把 AI 吐出来的整段 JSON 复制回来；
5. 粘进输入框，点「应用」；然后看结果里有没有被跳过的。

五个步骤里，**只有第 1 步和第 5 步是这个程序该干的活**。2~4 步是「程序没有翻译能力」
这个缺陷，硬塞给用户去补。这就是「繁琐」的全部来源。

还有三个隐性问题，比步骤多更伤：

- **没有记忆**：`Hoods` 在 cn 和 zh 两个文件里各出现一次，翻两遍；下次装了新模组，
  之前翻过的常见词还得再翻一遍。
- **没有术语**：每次交给不同的 AI，`Sign` 可能译成「法印」也可能译成「标志」，
  同一份界面里前后不一致。
- **反馈太粗**：应用完只说「改了 41 条」，剩下 4 条为什么没进去（太长放不下）
  得自己去翻结果列表。

## 一之二、一次纠错：汉化有三条通道，我们只认了一条

初稿把 AutoLoot 判成「没有中文语言文件」，用户当场指出：**它在游戏里是全中文的**。
查完之后承认判断错了，而且错得不浅：

模组的界面文字其实有三条来路：

| 通道 | 文字放在哪 | 本机实例 | 现版本能否处理 |
|---|---|---|---|
| **A. 语言表** | `content/cn.w3strings` | 15 个模组 | 能（等长替换） |
| **B. 脚本内嵌文本** | `.ws` 里按游戏语言分支 `return "…"` | AutoLoot（`modAutoLootLoc.ws`，**941 个中文字符**）、UI Remastered 指南针、UIRE 传送 | **完全看不见** |
| **C. 菜单 XML 字面文本** | `user_config_matrix/pc/*.xml` | 本机 0 条（几乎都是 key） | 能，但没活干 |

AutoLoot 属于 B：它自带一个 `AutoLoot_GetGameTextLanguage()`，按 `theGame.GetGameLanguageName()`
判断当前文本语言，然后从一堆 `if ( lang == "ZH" )` 分支里返回对应文字：

```
else if ( lang == "ZH" || lang == "CN" )
{
    return "[AutoLoot] 已跳过偷窃 - 附近有目击者或守卫！";
}
return "[AutoLoot] Steal skipped - witnesses or guards nearby!";   // 兜底英文
```

这种写法的模组**不该被算进「待翻」**：它已经翻好了，只是翻译不在语言表里。
现版本的结论「没有中文语言表」在字面上没错，但会让用户以为要去处理它 —— 这是错的。

顺便自查另外两个也被判「没有中文」的：

- **Swords On Hip**：它的英文串（`When cloaked`、`More Presets for Swords on the Hip`）
  全在**代码注释**里，不是界面文字。它没有菜单文字要翻。初稿把它列成待翻目标，也错了。
- **3 个「语言表加密」的模组**（Blood And Steel / PTOptimization / StandardisedNaming）：
  「加密」说的是**我们读不出原文**，不等于它没中文。它们游戏里可能显示得很正常，
  只是我们既不该改、也改不了。界面上必须把这两件事分开写。

**对 1.2.0 的直接影响**：

1. 汉化面板的分组要改成「待补翻 / 已经是中文（含脚本内嵌）/ 读不出原文（不动）」，
   AutoLoot 这类要归到第二组，并且注明「文字写在脚本里」。
2. 通道 B 只做**只读识别**（判断有没有中文、是不是按语言分支写的），
   **不做自动改写**：改 `.ws` 会动到脚本源码，风险等级和改语言表不是一个量级，
   等 A 这条链跑稳了再单独评估。
3. 「待补翻 45 条」这个数字本身没变 —— 但那是因为 B 通道本机已经全中文。
   将来遇到 B 通道仍是英文的模组，一键汉化会**漏掉**它，这一点要在界面上说清楚，
   不能让人以为「点完就全中文了」。

## 二、目标形态：勾几个模组、点一次、看一张表

要把「五个步骤」压成「勾选 + 一次点击 + 一次确认」。交互四步：

**第 1 步 · 勾选要汉化的模组（用户自己决定，程序不替他选）**

```
┌ 汉化 ──────────────────────────────────────────────────────┐
│ 翻译方式  Google ▸ MyMemory ▸ 百度(未配置)        ▸ 设置   │
│                                                             │
│ 要翻哪些内容   ☑ 菜单项  ☑ 分组名  ☐ 模组名  ☐ 物品名      │
│                                                             │
│ 勾选模组                          [全选]  [全不选]          │
│ ─────────────────────────────────────────────────────────── │
│ ☑ hoods Switchable Cloak        菜单 31 · 分组名 5          │
│ ☐ UI Remastered Edition         只有模组名（默认不改）      │
│ ☐ Hood Slots                    只有模组名（默认不改）      │
│ ☐ dlc Ronin Armor               只有物品名 4 条             │
│ ─────────────────────────────────────────────────────────── │
│   AutoLoot                     文字写在脚本里，已经是中文   │
│   Blood And Steel              语言表读不出，不动它         │
│                                                             │
│ 已选 1 个模组 · 36 条                      [ 开始汉化 ]     │
└─────────────────────────────────────────────────────────────┘
```

四条规则：

1. **勾选权在用户**：每个有可翻内容的模组前面都有勾选框，默认勾上「有可选条目」的，
   但用户随时能取消。程序不给「已启用 / 全部」这种固定选项代替他做决定。
2. **勾选是两级的**：上面勾模组，下面按内容类型筛。默认只勾「菜单项 + 分组名」，
   模组名与物品名默认不勾 —— 这就是「不推荐改模组名」的落地方式，不是禁止，是默认避开。
3. **不能翻的模组也占一行**，灰掉并写明原因（`语言表读不出` / `文字在脚本里`）。
   把它们藏起来会让用户误以为「这个模组没问题」，那正是上一版犯的错。
4. **没启用的模组照常列出**，行尾标一句「未启用，翻了要启用才看得见」。
   翻不翻由用户判断，程序只负责把事实说清楚。

**第 2 步 · 进度（可取消，断了能续）**

```
翻译中 19/36 …  记忆命中 6 · 网络 13 · 失败 0
当前引擎 Google（已用 13 次）      [ 取消 ]
```

**第 3 步 · 结果表（真正干活的地方）**

```
原文                                   译文              来源    状态
Enable for hoods/scarfs/masks          启用兜帽/围巾/面罩  Google  ✓ 已写
Auto equip force no animation          自动装备（无动画）  Google  ✓ 已写
Other                                  其他              Google  ⚠ 放不下（差 1 字节）
Deadly Ronin's Kimono                  致命的浪人服       Google  ✓ 已写
Switchable Cloaks by <font…>PRILER</font> 由 PRILER 制作的可切换披风  Google  ✓ 已写
```

表格里每一行都能直接改，改完可以「只重写这一条」；右下角一个「全部应用」，
**一次写入、一次撤销**。来源列写清是哪条通道翻的（`记忆` / `Google` / `MyMemory` / `AI`），
出了问题能立刻知道该怀疑谁。

**第 4 步 · 应用之后：备份已就位，随时能退回**

应用完不给一个「完成」了事，而是明确写出这次动了哪几个文件、备份在哪：
`已汉化 1 个模组 36 条，原文件已备份（点这里还原）`。详见第五节。

## 三、翻译引擎：一条链，一个挂了自动换下一个

这是能不能「一键」的前提。2026-10-28 把能想到的免 Key 端点全测了一遍，
**只有两个活着**：

| 端点 | 结果 |
|---|---|
| `api.mymemory.translated.net` | **200**，单条约 0.4 秒 |
| `translate.googleapis.com`（gtx 通道） | **200**，单条约 0.5 秒 |
| `translate.terraprint.co`（LibreTranslate 公共镜像） | 502 |
| `libretranslate.de` | 301 跳转后不可用 |
| `translate.fedilab.app` | 403 |
| `lingva.ml` | 403 |
| `edge.microsoft.com/translate/auth`（微软免 Key 通道） | 404，这条通道已经废了 |

结论很直接：**不能只绑一个接口**。只有一个能用的时候，它一挂整条链路就废，
用户看到的又是「汉化失败」。所以做引擎链，按顺序试，前面挂了自动用后面的：

| 级别 | 引擎 | 配置 | 实测 |
|---|---|---|---|
| L0 | 翻译记忆 + 术语表（本地） | 不要 | 命中即出，0 网络 0 成本，重复串与术语从此一致 |
| L1a | **Google 翻译**（gtx 免 Key） | 不要 | 质量最好，中文语序自然；国内网络可能不通 |
| L1b | **MyMemory**（免 Key） | 不要（可填邮箱提额） | 稳，质量中等；短词和带标签的句子容易出错 |
| L1c | **百度翻译** | appid + 密钥 | 国内最稳，免费额度够翻几万条 |
| L1d | **微软 / DeepL** | Key | 质量高，DeepL 尤其擅长整句 |
| L2 | **AI（OpenAI 兼容）** | Base URL + Key + 模型名 | 质量最好，能听懂「短一点」「保留标签」 |
| L3 | 复制成一段话 → 粘回 | 不要 | 离线兜底，就是现在这条路但改成一次性批量 |

### 为什么必须做「自动降级」：两个引擎的实际差别很大

同一条原文，2026-10-28 实测：

```
Enable for hoods/scarfs/masks
  MyMemory：启用连帽/围巾/口罩
  Google  ：启用头巾/围巾/口罩

Mod by <font color="#1FD655">PRILER</font> / Auto Unequip
  MyMemory：MOD BY <font color="#1FD655">PRILER</font>/AUTO UNEQUIP   ← 原样退回大写英文，等于没翻
  Google  ：由 <font color="#1FD655">PRILER</font> 修改/自动取消装备

Other
  MyMemory：其他种族          ← 短词没有上下文，直接译错
  Google  ：其他
```

MyMemory 对带标签的句子还有更严重的一种失败 —— 它把标签**挪了位置**：

```
原文：Switchable Cloaks by <font color="#1FD655">PRILER</font>
保护后：Switchable Cloaks by  [0] PRILER [1]
MyMemory 回：PRILER可切换斗<font color="#1FD655"></font>篷
```

颜色应用到了一个空串上，游戏里就是一个空的染色符号。所以：

**HTTP 200 不等于成功。** 三条判定，任何一条不过就换下一个引擎：

1. **原样退回**：译文去掉大小写和空白后与原文相同 → 失败。
2. **标签结构**：占位符的数量、顺序、位置都要和原文一致；还原后还要检查
   「每个标签是否还包着内容」。上面那个 `…<font></font>篷` 会被这一条拦下。
3. **长度**：超预算不算失败，但记一条「放不下」（见第七节）。

标签保护的实现：发送前把 `<font …>` / `</font>` / `<br>` 换成 `[0]` `[1]` 占位符，
翻完换回来。**两个引擎都会在标签内侧多吐空格**（`<font color="…"> PRILER </font>`），
还原时统一清掉 `> ` 与 ` <`。

### 多 Key：同一引擎可以存好几个

用户提的要求是「多配置几个 key，防止某些接口出问题时汉化失败」。两件事都做：

- **多个引擎**：上面那张表，顺序可拖动，前一个连续失败 3 次就临时让位。
- **同一引擎多个 Key**：百度/微软最容易撞日限额。每次请求取「最久没用过」的那个；
  某个 Key 回 401/403/限额 → 标灰 30 分钟，自动换下一个；全都不行就整级降级。

界面上是一张表：

```
引擎              密钥                    今日用量   状态
Google (免Key)    —                        —         ✓ 通 0.51s
MyMemory (免Key)  —                        13 条     ✓ 通 1.20s
百度              sk-…7f2a  sk-…3c91       0 条      ✗ 密钥无效
AI                sk-…a01b                 0 条      未测
                                        [ + 添加 Key ]
```

### 「测一下」按钮

配置完最怕的是「不知道通不通」。每个引擎后面一个「测一下」，用一句真实的菜单文字
发一次请求，回显**延迟 + 译文**：

```
Google      ✓ 通   0.51s   自动装备（无动画）
MyMemory    ✓ 通   1.20s   自动装备力无动画
百度        ✗ 401   密钥无效
```

延迟和译文都看得见，用户自己就知道该把哪个放前面。

### 为什么默认不是「必须配 AI」

用户是零编程基础，一个「请填写 API Key」的输入框会把「一键」变成
「先研究什么是 API Key」。默认必须打开就能用，AI 是「想要更好就换」的选项。

## 四、术语一致：一份能改的词表

内置一张巫师3 术语表（从 `witcher3/guide` 的定名基准抽：猎魔人、法印、突变、路牌、
昆特牌、刚特·欧迪姆、教主广场 …），存 `data/translate/glossary.json`，设置里可编辑。

两类引擎分别处理：

- **L2（AI）**：术语表作为硬约束写进提示词，「以下词必须这样译」。
- **L1（免费接口）**：接口听不懂约束，所以走**译后校正** —— 翻完扫一遍译文，
  命中术语的错误译法（比如 `Sign` → `标志`）自动替换成表里的标准译名。

翻译记忆 `data/translate/memory.json` 存 `原文 + 模组上下文 → 译文`，
命中就不发请求。同一串在不同模组里只翻一次；升级模组后旧译文仍然可用。
这也是「翻第二遍很便宜」的原因。

## 五、长度这道坎：只剩 1 条了，所以这一版不动文件结构

现在的写入方式是**等长替换**：只改文本块里的字节，偏移/长度/索引一律不动，
文件大小一模一样。好处是绝对安全，坏处是**译文不能比原文长**。

原来的方案里这件事很紧张：45 条里有 3 条撞上。但「不改模组名」这条口径确立之后，
**3 条里有 2 条（`Hoods`、`Hoods`）自动退出了待翻列表**，只剩 1 条：

| 原文 | 字节预算 | 中文需要 | 结果 |
|---|---|---|---|
| `Other`（菜单分组名） | 5 | 其他 6 字节 | **放不下** |
| ~~`Hoods`~~ | 5 | 兜帽 6 字节 | 模组名，默认不翻 |
| ~~`Hoods`（zh 表）~~ | 5 | 兜帽 6 字节 | 模组名，默认不翻 |

**为 1 条词条去改文件结构，风险收益不成比例。** 所以 1.2.0 的决定是：

- 只做**等长写入**（当前做法，零结构改动）；
- `Other` 这一条如实标「放不下（差 1 字节）」，并给两个建议：
  保持英文，或者手动改成单个字的缩写。用户自己定；
- **变长写入挪到 1.2.1**，默认关、可手动开，等这一版的一键链路跑稳几轮再说。

这个决定建立在已经做完的原型验证上（不是放弃，是押后）：

- 拿 `modLightRewrite/cn.w3strings`（4792 字节，114 条）当样本，
  把第 1 条从 `Light Rewrite`（13 字节）改成 `光影重写模组`（18 字节）；
- 按「文本块重建 + 索引表重算偏移」写回，文件变成 4797 字节（+5）；
- **回读校验：114 条全部逐字一致，键块原样未动，尾部填充保留。**

`.w3strings` 的结构是「头部 + 索引表 + 键块 + 文本块（在文件末尾）」，
索引里存的是**相对文本块起点**的偏移和长度。所以变长就是「重建文本块 + 重算偏移」，
不需要碰加密、不需要官方编码器。

> **2026-10-28 更正（这条结论我先前写错过）**
>
> 我一度判断「24 个语言表只有 4 个索引可读，所以变长写入基本用不上」。
> 那个判断是**解析器写错**导致的：我按「索引从 0x0C、每条 12 字节」去读 v164 文件，
> 而实际记录起点在 **0x0F / 0x10**（前面有 3 字节前缀），整体错位一位，数出来全是 0 条。
> 换成「从数据反推」的读法（找满足 `off[k+1] == off[k] + len[k] + 1` 的连续链，
> 同时试起点 8~63 与跨度 8/12），**绝大多数 v164 文件都能读出来**：
> `modLightRewrite` 114 条、`hoodsSwitchableCloak` 49 条、`UIRemastered` 421 条，
> 起点 0x0F/0x10、跨度 12。
>
> 所以「索引读不出来」在 1.2.0 里不该再当结论用。变长写入押后的真实理由是**下面那条**：
> 界面排版是按原文字节长度设计的，中文变长后可能超出菜单行宽被截断 ——
> 等长不只是保守，它在「别把界面撑坏」这件事上本来就更对。

将来变长写入上线时按三档处理：

| 档 | 条件 | 处理 |
|---|---|---|
| A | 译文装得下 | 等长写入（1.2.0 全部走这条） |
| B | 装不下，但索引可读 | 变长写入：临时目录重写 → 回读逐条校验 → 通过才落盘 → 失败保留原文件 |
| C | 装不下，索引也不可读 | 标注「放不下」，给建议短译，用户自己决定 |

## 五之二、备份与还原：汉化出错必须能一键退回去

这是用户明确要求的一条，而且它是「敢不敢点一键」的心理前提。
现有的 `safety.Operation` 已经能快照 + 记账 + 撤销，但**不够用**，有两个洞：

1. **快照只保留最近 30 份**（`prune_snapshots(30)`）。用户汉化完又装了十几个模组，
   汉化前的原件就被清掉了 —— 那时想还原已经没有东西可还原。
2. **没有「历次汉化」的视图**。journal 是通用的写入流水，混着安装/卸载/改顺序，
   用户不可能从里面挑出「上周三那次汉化」。

所以单独加一层，不动现有机制：

```
data/localize/
  orig/<模组>__cn.w3strings        第一次汉化该文件时的原件，永久保留，永不覆盖
  history/<时间戳>/<模组>__cn.w3strings   每次汉化前一份
  index.json                       每次汉化的记录
```

`index.json` 一条长这样：

```json
{"id":"20261028-180233", "time":"2026-10-28 18:02:33",
 "scope":[{"mod":"mod_hoodsSwitchableCloak","lang":"cn","entries":36,
           "before":"history/20261028-180233/mod_hoodsSwitchableCloak__cn.w3strings",
           "sha_after":"9f2c…"}],
 "engine":"google", "note":"36 条"}
```

界面上是汉化面板底部一个「汉化记录」区，每行一次操作：

```
2026-10-28 18:02   hoods Switchable Cloak · 36 条 · Google     [还原] [还原到最初]
2026-10-28 17:40   hoods Switchable Cloak · 12 条 · MyMemory   [还原] [还原到最初]
```

四条规矩：

1. **`orig/` 永不覆盖。** 第一次汉化某个语言表时存一份，之后无论翻多少次都不动它。
   所以「还原到最初」永远可用，哪怕翻了二十遍。
2. **还原也走 `Operation`。** 还原前先把当前文件快照一次，所以「还原」本身也能撤销 ——
   点错了不至于两头空。
3. **还原前校验指纹。** 记录里存的是「汉化后应有的 sha256」。还原时先算当前文件的
   指纹，对不上说明**这段时间文件被别的东西改过**（mod 更新了、用户手动改了、
   别的汉化工具动过）。这种情况不直接覆盖，而是弹一句：
   「这个文件在你上次汉化之后又被改过（可能是模组更新）。还原会把那次改动一起冲掉，
   确定吗？」—— 让用户自己判断，程序不替他决定。
4. **按次还原 = 按模组还原。** 一次汉化可能动了多个模组、多个语言表，
   但记录的是同一批，还原就是整批回去，一次点击、一次撤销。
   如果只想退某一个模组，记录行里能展开，单独勾。

`history/` 保留最近 20 次（约几百 KB），更早的自动清；`orig/` 不参与清理。
`storage.py` 的清理列表里要显式排除这两个目录 —— 那是用户的退路，不是缓存。

## 六、说清楚做不到什么

不写的部分要提前讲明白，免得用户以为「一键」能解决一切：

- **语言表加密的模组翻不了**（本机 3 个）。原文在加密块里，读不出就没有可翻的东西。
  程序不去猜密钥 —— 猜错了写回去就是一屏乱码。
  **注意措辞**：这只说明我们读不出，不代表它没中文；界面不能写成「这个模组缺中文」。
- **文字写在脚本里的模组（通道 B）不自动改写**。能识别、能告诉你在哪，
  但改 `.ws` 源码风险不同量级，留到后续版本单独评估。
- **贴图/模型上的字**完全不覆盖，那不是文本资源。
- **免费引擎的译文质量**是「能读懂」级别，术语靠词表校正，不是官方译名水准。
  想要更好只能配 AI。
- **不联网也能用**，但只能走 L0 记忆 + L3 复制粘贴；第一次翻新词必须联网或用 AI。

## 附：这次实测用到的解析要点（技术备查）

```
0x00  RTSW
0x04  u32  版本（162 / 164；重制版 5.00 = 164）
0x08  u32  未明（各文件不同，写入时原样保留）
      索引表起点**不固定**：实测 v164 在 0x0F 或 0x10，v162 有 0x33 的，
      前面还有 3 字节前缀（04 字符 + 未明）。**别写死 0x0C** ——
      我按 0x0C 对齐读，整整一批文件被判成「索引不可读」。
索引表  每条 12 字节：文本偏移 u32 | 文本长度 u32 | id u32
      偏移相对「文本块起点」，长度不含结尾 NUL，条目间恰好隔 1 个 NUL
      条目数不写在头部 —— 靠「偏移连续递增」判定结束：
          off[0] == 0 且 off[i] == off[i-1] + len[i-1] + 1
键块  索引表之后到文本块之前，写入时原样搬运
文本块 位于文件末尾，之后仅有 ≤3 字节填充
```

索引布局不用猜，反推就行 —— 试起点 8~63、跨度 8/12，看哪组能串出最长的
`off[k+1] == off[k] + len[k] + 1` 链。真实数据上这个办法一次就命中了
（`modLightRewrite` 114 条 @0x10、`hoodsSwitchableCloak` 49 条 @0x0F、
`UIRemastered` 421 条 @0x10，跨度都是 12）。

文本块起点的定位办法：从索引表结束处向后试，第一个能满足「所有条目在
`base+off` 处都是合法 UTF-8、且 `base+off+len` 处正好是 0x00」的位置即为起点。
这个判定本身就是写入前的结构校验 —— 做不到就说明这份文件不该被变长改写。
