# Waass 1.0.9 → 1.1 交互改版交接说明

> 给执行 agent。本文只写「改什么、为什么、验收怎么算、哪里可能崩」，不写实现代码。
> 依据：`docs/competitive-review-2026-10-27.html` 第七、八、九节。
> 所有行号基于 **1.0.9 快照**。若代码已变动，以实际为准并在产出里标注偏差，**不要按行号盲改**。

## 0. 一句话

把三处 P0 交互缺口（批量操作、卸载静默失败、`prompt()` 输入）和一层 Win11 视觉令牌一起做，产出 1.1.0。视觉层不新增功能，只是给已排期的功能换皮。

## 1. 相对上一版报告改了什么

| 项 | 旧版 | 现版 | 原因 |
|---|---|---|---|
| 主列表线框 | 表格（名称/状态/顺序 + 首列复选框） | **卡片网格 + 缩略图不裁 + 卡角复选框 + 密度三档** | 缩略图是认 mod 的主要线索；187 个 mod 光看名字分不清谁是谁。表格是 MO2 的范式，它本来就没图 |
| 视觉方向 | 无 | 新增第九节 | 用户认可 Win11 方向，但分层：系统同源必做 / 材质语言可换 / 纯模仿不做 |
| 密度 | 未提 | 三档 loose·standard·compact | 卡片内解决密度，不牺牲图 |

**结论：不要为了密度砍缩略图。** 紧凑列表视图保留，当作三档里最紧的一档，不另做一套。

## 2. 不变量（动手前必须接受）

1. `core/guard.py` 仍是唯一写入闸门。本次改动**不得新增任何绕过 guard 的写路径**。
2. 扫描永远只读；`mods.settings` 仍零注释、段间恰好一空行（Script Merger 解析器不容忍注释）。
3. 技术栈不变：Python 标准库 + 原生 HTML/CSS/JS。不引框架、构建工具、外部字体 CDN。
4. `mods.settings` 只有一处写入口（`core/actions.py`）。批量操作必须走同一个入口，**不许前端循环调用单条接口**。
5. 视觉层不得新增任何出站网络请求。
6. `witcher3.exe` 在跑时拒绝一切写；这条已有（`core/safety.py:132`），不要因为批量新接口绕开。

## 4. 批次 A · 视觉令牌（对应报告 S1 + S2）

### A1 明暗跟随系统

**改**：`S.theme` 从两态改成 `auto / light / dark` 三态。`auto` 时用 `matchMedia('(prefers-color-scheme: dark)')` 取值，并监听 `change`；用户点按钮后变成显式覆盖并写 localStorage。

**文件**：`app.js:12`、`:922-924`、`:987`；`index.html:2`（`data-theme` 初值）、`index.html:13`（已有内联脚本设 token，可在同处提前设 `data-theme` 避免首帧白闪）。

**验收**
- 系统深色 → 启动即深色，窗口标题栏与页面同色，不出白闪。
- 不刷新页面切换系统主题，界面跟着变。
- 点过按钮后不再跟随系统；设置页能改回「跟随系统」。

**风险**：老用户 localStorage 里已有 `'light'`/`'dark'`，会被当成显式覆盖，表现为「新功能没生效」。迁移策略二选一，**请在评估时选一个**（见 §10 Q4）。

### A2 系统强调色

**改**：Python 读 `HKCU\Software\Microsoft\Windows\DWM` → `ColorizationColor`（DWORD，`0xAARRGGBB`），注入 CSS 变量 `--accent`。

**文件**：新增 `core/theme.py`（读注册表 + 进程内缓存）；`server.py` 在首页模板渲染处多注入一个占位符（照抄 `%%WAASS_TOKEN%%` 的替换方式）。
**同样的读法项目里已有两处**：`core/paths.py:84`、`core/downloads.py:44`。

**派生色交给 CSS，不要在后端算十六进制**
```css
--accent:      <注入值>;                                        /* 系统强调色 */
--accent-soft: color-mix(in srgb, var(--accent) 12%, var(--panel));
--accent-line: color-mix(in srgb, var(--accent) 45%, var(--panel));
--accent-ink:  color-mix(in srgb, var(--accent) 72%, #000);
```

**验收**
- 改系统强调色 → 重开软件后主色同步。
- 读不到键 / 值异常 → 回落 `#4F46B8`，不报错、不刷日志、不影响启动。
- 把系统强调色设成浅黄、浅绿各试一次：**主色上的文字仍可读**（这正是要 `--accent-ink` 的原因，别直接把白字压在原色上）。

**风险**：系统强调色可能是极浅色，白字必然不可读。所有「做主色底」的组件（启用态按钮、选中描边、badge）都要重新校对比度，不能只改 `--accent` 就收工。

### A3 字号阶梯 + 圆角 + 控件高

**改令牌，别逐条改组件**

| 参数 | 现状 | 目标 |
|---|---|---|
| `--radius-lg`（卡片） | 12px | 8px |
| `--radius-xl` | 14px | 并入 8px 或删除 |
| 控件圆角 | 7px | 4px |
| 控件高（`select` / `seg` / 按钮） | 30px / 28px | 32px |
| 最小字号 | 存在 10px、10.5px | 12px（Win11 Caption）。`.side-title`、`.card-sub`、`.path-label`、`.badge`（9.5）都要抬 |
| 侧栏宽 | 218px | 236px（12px 中文撑不开 218） |
| 字体栈 | `system-ui` 起头 | `"Segoe UI Variable Text"` 起头，中文仍回落 `Microsoft YaHei UI` |

**连锁验算（请复核，这是我算的）**
- 1920 宽：中栏 1920−236−322−36 = 1326 → 无损。
- 1366 宽：1366−236−322−36 = 772 → 4 列需 4×162+3×12 = 684，有余量。
- 1280 宽：1280−236−322−36 = 686 → 恰好 684，**零余量**。这里要么卡片最小宽降到 152px，要么侧栏只加到 226px。**请在评估时定。**

**验收**：1280×800 与 1920×1080 各看一次，无横向滚动，无「只剩省略号」的标题。

**风险**：字号上调会让卡片高度从 ~140px 涨到 ~146px，一屏少半行——这是这一批唯一真实的代价，用户已认可。

## 5. 批次 B · 卡片多选（P0，功能）

### B1 数据模型

- `S.sel: Set<string>`：多选集合。
- `S.selected`：保留现有语义，改名/别名为 `S.focus`（详情面板跟随它），避免全局重命名带来的风险。
- 合订本（`m.is_merged`）**不进多选**，但可以被选中作为焦点。

### B2 交互

| 动作 | 行为 |
|---|---|
| 复选框（缩略图左上） | 只切换 `sel`，**不改变焦点、不触发 `select()`** |
| 复选框可见性 | 默认 0.35 透明度；卡片 hover 或 `sel.size > 0` 时 1 |
| 点卡片体 | 聚焦 + 清空 `sel` |
| Ctrl+点击 | 切换该项的选中，不改焦点 |
| Shift+点击 | 从当前焦点到该项范围选中（可放 P2，先不做也行） |
| Ctrl+A | 全选**当前筛选结果**（不是全部 187） |
| Esc | 清空 `sel` |
| 选中后工具条 | `已选 N` · 全选 · 启用 · 禁用 · 加入分组 · 取消 |

- 工具条插在 `.content-head` 的 `.content-tools` 位置（`index.html:83-99`），替换 `viewMeta` 那一行，不要新加一条横条——现在顶部已经两层（topbar + content-head + warnBar）。
- 详情面板（`app.js:417` 起）显示「已选 N 个」，批量动作与工具条共用一份状态。
- 选中态视觉：卡片 1.5px 强调色外描边（`inset box-shadow`，与现有 `.card.is-on` 同法，`style.css:411-414`）。

### B3 后端（这条最关键，别在前端循环）

**必须新增批量入口**

```
core/actions.py: set_enabled_many(root, keys: list[str], enabled: bool) -> dict
POST /api/mods/batch_toggle  {keys: [...], enabled: bool}
返回 {done: [...], failed: [{key, error}]}
```

内部要求：`safety.authorize_game` 一次；**一个 `Operation`**；`_ensure_merged_entry` 只跑一次；`settings.save()` 一次；`op.commit()` 一次；`STATE.patch_mod` 按成功项批量回写。

**为什么不能循环调单条**：每次 `set_enabled` 都会新建 `Operation`（`core/safety.py:162`）→ 复制一份 `mods.settings` 到 `data/snapshots/<id>/`，再全量重写一次文件并跑一次合订本护栏。禁 25 个 mod 就是 25 份快照、25 次全量重写、25 条 journal；用户点一次「撤销」只回滚最后一条。既慢又恢复不了。

**验收**
- 选 10 个禁用 → `data/snapshots/` 只多 **1 个** 目录；`journal` 多 **1 条**，label 形如「批量禁用 10 个」。
- 点一次撤销 → 10 个全部回到原状态。
- 其中 3 个 mod 文件夹被人手动删了 → 返回 7 成功 + 3 失败，界面明确列出失败项，**不整体回滚、不静默**。
- 游戏运行中调用 → 409，前端提示，不产生任何写入。

### B4 非目标（明确不做）

- 批量拖拽排序、批量改优先级
- 跨筛选记忆选择
- 多选后导出/打包
- Shift 范围选择的精细语义（可留到 P2）

## 6. 批次 C · 其余 P0（报告已详述，此处只给验收）

**C1 卸载配置冲突改成阻塞确认**　`install.js:307-311` 现在是 7 秒 toast。
验收：卸载时若有 `merge_conflicts`，弹出阻塞对话框，说明「有 N 处配置被别的程序改过，没强行还原」，三个出口：还原备份 / 保留现状 / 取消卸载。**绝不能只 toast**——用户会以为按键绑定丢了。

**C2 `prompt()` 换站内输入框**　`app.js:611`（建分组，`app.js:929` 与 `settings.js:175` 是路径粘贴，同一个问题）。
验收：站内输入框，有校验、可取消、可 Esc 关闭。这与 `SPEC §11「必须原生对话框」` 不冲突：那条针对的是**选文件/选目录**，不是文本输入。

**C3 空状态三出口**　`index.html:106-109`。
验收：空状态给出三个动作——清空搜索/筛选、去「全部模组」、导入压缩包。当前只有一句话。

**C4 游戏运行中全局只读**　现在只禁用了撤销按钮（`app.js:347-348`）。
验收：`game_running` 为真时，顶部出现常驻 banner（说明为什么不能写），所有会写盘的按钮 disabled + 有原因提示，卡片开关置为不可点。避免用户点二十下才发现全失败。

## 7. 批次 D · 密度三档（对应 S4）

**改**：`#mods` 上挂 `data-density="loose|standard|compact"`，只动 CSS 变量，不加 JS 模式分支。选择存 localStorage。

| 档 | 卡片最小宽 | 封面高 | 名字 | 副标题 |
|---|---|---|---|---|
| loose | 200px | 112px | 13px | 显示 |
| standard（默认） | 162px | 88px | 13px | 显示 |
| compact | 118px | 64px | 12px | 隐藏 |

**验收**：三档切换后同一块区域分别约显示 12 / 16 / 26 个，**缩略图在所有档位都还在**。

**风险**：compact 档卡片只有 118px，左上角复选框会压住封面主体。允许 compact 档改成「悬停才显示复选框」，但选中数必须始终在工具条可见。

**可选**：如果评估后认为三档收益不足，**保留 standard + 现有列表视图（`style.css:473`）即可**，不阻塞 1.1.0。请给判断。

## 9. 风险与回滚

- 全部改动可分四批独立合入，A / B / C / D 互不依赖（B 的复选框视觉依赖 A3 的圆角令牌，但可先落后调）。
- 视觉层回滚成本极低：令牌集中在 `style.css:5-45`，还原即可。
- B3 新增端点属于**新增写路径**，合入前必须过 `guard` 的沙盒测试；这是唯一有数据风险的一批。
- 不建议为了赶进度把 B3 降级成「前端循环」——那会把可撤销性做坏，比不做更糟。

## 10. 请你评估的 6 个问题

1. **A3 的 1280 宽零余量**：降卡片最小宽到 152，还是侧栏只加到 226？
2. **强调色注入方式**：模板占位符替换 vs 新增 `GET /api/theme` 端点，哪个更贴合现有架构？现有 `server.py` 用的是 if 链分发（`:197`、`:356`），请按现状判断。
3. **B3 是否顺带覆盖批量加入分组**：同一个 `Operation` 能不能复用？还是分组只改 `library.json`、不进快照？
4. **老用户 localStorage 的显式 light/dark**：一次性迁成 `auto`，还是保留为手动选择并引导？
5. **密度三档**：值不值得做，还是固定 standard + 列表视图就够？
6. **是否先做 A1 最小验证**：只改主题跟随（约 15 行），先给用户看效果，再决定要不要上强调色与字号重排？
